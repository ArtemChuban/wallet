# Quick Task 260908-0i7: Merge debit, crypto, and cash account types into one type (asset/debit); keep credit separate; migrate existing data; difference only in currency - Context

**Gathered:** 2026-09-08
**Status:** Ready for planning

<domain>
## Task Boundary

Merge `FIAT_DEBIT`, `CRYPTO`, and `CASH` into one account type. Keep `FIAT_CREDIT` as a separate type with credit-specific fields. Difference between former debit/crypto/cash is currency only, not account type.

<decisions>
## Implementation Decisions

### Canonical type name
- **D-01:** New enum value: `ASSET`
- **D-01:** `FIAT_CREDIT` remains unchanged
- **D-01:** Former `FIAT_DEBIT` / `CRYPTO` / `CASH` semantics unify under `ASSET`

### Migration strategy
- **D-02:** Soft compat: writes use only `ASSET`; reads still accept legacy `FIAT_DEBIT` / `CRYPTO` / `CASH` until a later cleanup pass
- **D-02:** Do not hard-drop old enum values in this quick task
- **D-02:** Existing rows may stay on legacy types for now; new/edited accounts persist as `ASSET`

### Create/edit UI
- **D-03:** Single “Asset” choice + currency picker only
- **D-03:** No crypto/cash/bank type chips or presets that fake separate types

### Cash / crypto currency rules
- **D-04:** `ASSET` accepts any allowed currency (fiat codes + crypto codes such as USDT on the same list)
- **D-04:** No hard type↔currency lock after merge

### Claude's Discretion
- How soft-compat is expressed in Prisma/Zod (e.g. keep enum members + normalize on write, or dual schema read/write)
- Where to normalize legacy types for display/grouping (treat as ASSET in UI)
- Seed/test fixture updates needed for soft-compat path
- Exact Russian/English labels for “Asset” in UI

</decisions>
